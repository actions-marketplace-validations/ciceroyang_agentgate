# 2,057 个 MCP server,审计跑完的是 264 个

*2026 年 9 月。数字来自 2026-09-17 用扫描器 `25d846c` 构建的索引。算这些数字的脚本就在仓库里,命令在文末。*

每个安全工具都有一个该小心的词,这个词是"干净"。一条发现只是让人多看一眼;一个干净结论是让人不用再看了。所以我这周没看扫描器发现了什么,而是数了一遍:它到底有多少时候有资格下这个结论。

## 数字

索引里 2,057 个 MCP server,**其中 264 个(12.8%)有完整的覆盖块**——这条记录要求的扫描器都跑完了,输出在、能读、且不自相矛盾。剩下 1,793 个没有。

这是本站最不好看的数字,所以它就在这。

## 剩下的是什么挡住了

几乎全是一件事:

| 没跑成的部分 | 记录数 | 原因 |
| --- | ---: | --- |
| registry document | 1,782 | `not-audited` |
| package manifest | 11 | `metadata-unavailable` |

1,782 个 server 的注册表文档从来没被审过。其中 1,767 个压根没有列任何 npm 或 PyPI 包——它们是托管型或远程 server,我这条流水线会读的第一份文档对它们根本不存在。剩下的 11 个确实发布了包,是拉取注册表元数据失败了;失败被记成失败,没有被记成"没有结果"。

这些都不说明那些 server 危险。它说明我的方法现在还够不到它们,而我宁愿索引显示一个洞,也不愿在一个洞上面盖一块绿色的方块。

## 那 1,991 个"干净"去哪了

9 月初,我的索引说 2,072 个 server 里有 1,991 个干净。流水线的做法和大多数工具一样:能采的采,采到的东西里没有发现,其余就按干净发布。采集那边其实知道得更多——census 一直在记一个 `audited` 标志,只是索引没读它。

索引开始读它的那天,clean 从 1,991 掉到 195,incomplete 从 60 涨到 1,845。那天 server 本身没有任何变化。变的是:工具不再把没读过的材料算成通过。

覆盖块就是那次修正的逐条版本。现在打开任何一个 server 的页面,都能读到哪个扫描器是必需的、哪个跑完了、没跑成的那一个挂着什么原因——而不是从"没有发现"里反推这一切。

## 跑完了,不等于能打分

还有第二类,这一类更有意思。**有 38 条记录,所有必需的扫描器都跑完了**,覆盖块写着 `complete`,结论却仍然是 `incomplete`。

原因还是同一条规则,下沉了一层:那些扫描的发现里,severity 是 `unknown`。"unknown"和"low"不是一回事。它表示检查跑了、但得不出结论;而一个没法排序的 severity 会被当成"没测量"。所以它既撑不起一个干净结论,也没法拿去跟阈值比。扫描器跑了,你依然可能没法给结果打分。

## 采到了什么

465 条发现,分布在 274 个 server 上:critical 11、high 13、medium 28、low 17、unknown 49、informational 347。`clean` 的含义是"没有达到 medium 或以上的发现、也没有 unknown severity",不是"清单是空的"。

## complete 不表示什么

- 不表示 server 安全。它表示这条记录要求的扫描器跑完了。
- 不表示所有可能的检查都做过;它表示必需的那些做过,而且清单就在记录里。
- 不说明 server 所在机器、配置或运行时行为。那些不是公开材料。
- 这是我们对公开材料的测量,不是第三方评估。

底下那条规则才是重点:**只要有一部分没测量,结论就是 `incomplete`,永远不是 `clean`**。覆盖块的存在,是为了让这条规则成为一个你能读的字段,而不是一句你得选择相信的承诺。

## 复现

```sh
node scripts/coverage-stats.mjs --index data/index.json
```

它打印的就是上面这些数字;如果任何一条记录声称的结论是它自己的覆盖块撑不起的,它会以非零退出。记录格式见 [docs/spec/scan-execution-v1.md](../spec/scan-execution-v1.md),旁边有 JSON Schema。同样的数据公开在 [/v1/index/summary](https://xn--5kvo87g.com/v1/index/summary) 和 [/evidence.html](https://xn--5kvo87g.com/evidence.html)。

如果你在维护一个 MCP server,这类审计的起点是你发布的一份文档——注册表条目、包清单。发布它,是让这种检查成为可能的第一步。如果你在用这些 server,可以把你的清单放进 [/inventory.html](https://xn--5kvo87g.com/inventory.html),逐条看哪些扫描器跑过、哪些没跑过。
